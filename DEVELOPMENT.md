# Development log and research note

## Building the documentation

The three workflow vignettes and the technical algorithm guide are the source
for both R's installed documentation and the pkgdown articles. Build from the
repository root with R, Pandoc, and the package dependencies installed:

```r
install.packages(c("pkgdown", "knitr", "rmarkdown", "svglite", "dagitty"))
pkgdown::build_site(devel = FALSE, preview = FALSE)
```

This installs the current source package for the build, executes article and
reference examples, and writes a reviewable site to `_site/`. Open
`_site/index.html` locally. The site has its own concise homepage in
`pkgdown/index.md`; the six evaluation figures remain in the README. Generated
site files are ignored by git and excluded from the source package. The existing
`docs/algorithm.html` is a historical standalone rendering; the site uses the
current `vignettes/algorithm.Rmd` instead.

The homepage illustration is generated by `Rscript pkgdown/render-overview.R`
from the getting-started graph, after installing the current package. It lives
in `man/figures/` so pkgdown can copy it without depending on article build order.

`R CMD build .` builds the installed vignettes; `R CMD check --no-manual` on the
resulting tarball also checks their code. The standard package-check workflow
already runs these steps. The separate Documentation workflow builds the site
on pull requests and pushes to main, installs DAGitty so the optional examples
run, and uploads `metrodag-documentation` as a review artifact. Core plotting
examples and temporary-file exports run during vignette builds; only installation
commands and the example writing into a user's project directory are unevaluated.

Enable **GitHub Actions** as the publishing source under **Settings > Pages**.
The repository is private, so Pages availability depends on its GitHub plan.
Review the public site contents and the URL in `_pkgdown.yml` before enabling
Pages. Pushes to `main` publish the built site once Pages is configured. For a
manual deployment, run **Documentation** on `main` with **publish** enabled.
Pull requests build a downloadable preview through the same workflow. The
workflow stages the source without the development log and roadmap so the
website contains the package documentation.

## Preparing a CRAN submission

Update `DESCRIPTION`, `NEWS.md`, and `CITATION.cff` to the same release version.
The R citation reads the version from `DESCRIPTION`. Update its year when
preparing a release in a new year. Build a source tarball and check it with
R-devel and the optional packages installed:

```sh
R CMD build .
R CMD check --as-cran metrodag_0.3.0.tar.gz
```

The routine package check exercises the public workflows in a shorter test
suite. Set `NOT_CRAN=true` to run the full suite during package checks, as the
release and old-release GitHub jobs do. The R-devel job exercises the CRAN
test selection, and the no-Suggests job runs it with only Depends and Imports
(and testthat) installed, so the noSuggests check needs no manual run. The
R 4.1 job checks the declared floor and does not block yet. The weekly run,
which can also be started by hand, checks against development ggplot2 and
patchwork and writes covr coverage, `urlchecker::url_check()` and
`spelling::spell_check_package()` results to its summary; read the latest one
before a submission. Test files run in parallel; "Running the tests" in
`CONTRIBUTING.md` shows how to set the number of workers and how to run the
CRAN selection against ggplot2 3.4.4 before merging. The GitHub README and its
benchmark figures stay in the repository. The source tarball includes the four
built vignettes and the canonical metrics used by a regression test.

Before submitting, verify the maintainer address and all public links, and
update `cran-comments.md` with the results for the exact tarball. Use the
[CRAN submission form](https://cran.r-project.org/submit.html) and confirm
the submission email as the package maintainer.

## 2026-10-01 — scope and architecture

The first milestone uses the established layered-drawing decomposition:

1. validate a directed acyclic input;
2. assign strict topological layers;
3. reduce crossings with alternating barycenter/median sweeps;
4. place nodes on a regular grid;
5. identify visually preferred continuations with a deterministic greedy path
   cover; and
6. route each edge as a monotone polyline over vertical and 45-degree steps.

This ordering keeps DAG semantics primary. Rotation happens only after valid
downward geometry has been computed. A uniform vertical layer gap is enlarged
when needed so every endpoint pair admits an octilinear monotone path.

## Focused prior-art review

* Sugiyama, Tagawa, and Toda introduced the canonical layered framework:
  hierarchy/rank assignment, ordering, then coordinate assignment. MetroDAG is
  an application of that framework, not a replacement for it.
* Gansner et al.'s `dot` describes a practical four-pass implementation:
  ranking, within-rank ordering, coordinate assignment, and spline generation.
* Brandes and Köpf address fast horizontal coordinate assignment while balancing
  straight inner segments. Their alignment/conflict machinery is a likely next
  improvement over the MVP's centered integer coordinates.
* Barycenter and median sweeps are fast heuristics for the NP-hard two-layer
  crossing problem. They provide a defensible interactive default, but no
  optimality guarantee.
* Upward drawing supplies the relevant semantic constraint: directed edges must
  be monotone in a common direction. Orthogonal/octilinear drawing alone is not
  sufficient because it is normally direction-agnostic.
* Stott et al. formulate metro schematization as multicriteria optimization of
  angular resolution, edge length, line straightness, and octilinearity. This
  vocabulary is useful, but geographical displacement and metro-line topology
  are not the governing constraints for a causal DAG.

### `graphlayouts::layout_as_metromap()` audit

Inspection of graphlayouts 1.2.5 found an MIT-licensed C++ hill climber based on
Stott et al. It requires both a graph and initial `xy`, snaps stations to a grid,
and moves each station among eight adjacent positions inside a bounding box. Its
objective combines angular resolution, preferred edge length, balanced incident
lengths, line straightness, and octilinearity. The source explicitly marks line
straightness as unimplemented and its documentation warns about instability and
parallel edges. It returns node coordinates, not routed polylines. It neither
assigns DAG ranks nor enforces upward monotonicity, so it is prior art for the
soft schematization terms rather than a suitable DAG engine. No code was copied.

## Alternatives considered

* **Generic metro optimization:** rejected because it can invert causal
  direction and assumes a meaningful geographical starting layout.
* **Force-directed initialization:** rejected as the deterministic default; it
  ignores rank semantics and makes repeated figures unstable.
* **Strict orthogonal routing:** retained for future comparison, but horizontal
  segments can make progression ambiguous. Restricted monotone octilinear
  routing is the MVP default.
* **Generic edge bundling:** rejected for now because merged trunks obscure
  edge identity. Ordered parallel lanes are a future experiment.
* **Global ILP:** useful as a small-graph benchmark, but unsuitable as a light,
  interactive default and likely to require a heavy solver dependency.

## Findings and failure cases

Node ordering offers the largest cheap improvement: it prevents avoidable
inversions before routing. The simple router is structurally reliable but can
overlap unrelated edges and pass through unrelated nodes. Enlarging every layer
gap for one difficult edge wastes vertical space. Dense bipartite layers remain
the key adversarial family: crossings are unavoidable, arrowheads crowd sinks,
and the path-cover metaphor becomes weak.

The current path cover is metadata only. This is deliberate: moving nodes to
force a selected chain straight can increase crossings, and that trade-off must
be evaluated by a combined objective rather than intuition.

## Research questions and present evidence

RQ1–RQ2 cannot honestly be answered without a controlled perceptual study. The
implementation enables such a study but does not substitute geometric metrics
for human evidence. RQ3 is explicit in the planned cost function. RQ4 currently
favors no shared trunks because traceability is a hard concern. RQ5 remains
graph-family dependent. For RQ6, established literature and initial design
analysis indicate that ordering is the most cost-effective first step. RQ7
requires comparison with an exact small-graph formulation.

## Novelty assessment

Layering, median/barycenter ordering, dummy vertices, path covers, upward
drawing, octilinear routing, and metro-map multicriteria optimization are all
established. Merely combining them is not enough to claim novelty. A potentially
publishable contribution would require a precisely defined monotone-octilinear
causal-DAG objective, a routing/continuation algorithm with a new guarantee or
strong empirical result, exact small-instance baselines, and a perceptual study.
The package currently makes no novelty claim.
